# 로컬 실행 검증 (2026-09-24)

Windows Python 3.13.9, Docker PostgreSQL 16 + pgvector, 설치된 Ollama로 실행했다.
저장소의 컨테이너 Python 버전은 3.12이며 이번 검증의 API는 Windows에서 직접 실행했다.

- DB: `127.0.0.1:55432` (기존 5432 포트와 분리)
- API 및 웹 화면: `http://127.0.0.1:8000`
- 임베딩: `bge-m3`, 1024차원
- 생성: 기존 설치 모델 `qwen3.5:2b`, 컨텍스트 8192

|---|---:|---:|

6개 문서 모두 `indexed` 상태를 DB에서 확인했다. 기존 기록보다 청크가 늘어난 것은
짧은 PDF 본문 보존과 긴 산문 분할을 적용했기 때문이다.

## 확인한 동작

- 자동 테스트 9개 통과 (`RUN_DB_TESTS=1`): Office 위치, 짧은 PDF 본문, 긴 산문,
  인용 번호 검증, API 입력 검증, Windows glob, 실제 DB 색인·검색·업로드·재색인.
- 모델 실패 시 재색인 전 데이터가 검색 가능한 상태로 남는지 확인.
- `/ready`: DB와 Ollama 모델 모두 준비 완료.
- 실제 질문 “SR630 V4 최대 메모리 용량은?” → “8TB”, 출처 `p14`.
  반환한 발췌: `Memory maximum: Up to 8TB by using 32x 256GB 3DS RDIMMs`.
- 미등록 모델 `SR999 V9` → “제공된 문서에서 찾지 못했습니다.”, 출처 0개.

실제 질의 점검은 `python tools/check_local.py`로 재실행할 수 있다.
이는 동작 확인이며 전체 문서의 답변 정확도나 Recall을 측정한 결과는 아니다.
업무용 정답표 30~50개에 대한 품질 평가는 별도로 수행해야 한다.
