# 기술 결정 기록

각 결정의 **근거와 포기한 것**을 남긴다. 나중에 "왜 이렇게 했지"를 다시 묻지 않기 위해서다.

---

## D1. 구현 언어는 Python

**결정.** Python 3.12 + FastAPI.

**근거.** 이번 PoC의 지식 소스가 PDF/Office 문서다. 표와 다단 레이아웃이 섞인
사내 규정집·제안서·스펙시트를 제대로 뜯으려면 파서 품질이 결과를 좌우하는데,
`PyMuPDF`·`unstructured`·`docling` 등 실전에서 검증된 도구가 Python에 몰려 있다.
사내에 Ansible·운영 스크립트 경험이 있다면 Python 친숙도도 유리하다.

**포기한 것.** TypeScript 단일 스택의 단순함. 프론트엔드를 붙일 때 언어가
둘로 나뉜다. 다만 PoC 단계에서는 UI보다 파이프라인 품질이 중요하다고 판단했다.

---

## D2. 벡터 저장소는 별도 DB 대신 pgvector

**결정.** PostgreSQL 16 + pgvector.

**근거.** "구조가 깔끔한 게 좋다"는 요구에 대한 직접적인 답이다.
전용 벡터 DB를 두면 문서 메타데이터는 A에, 벡터는 B에 있게 되고 둘의 정합성을
애플리케이션이 책임져야 한다. pgvector는 문서·청크·벡터·전문검색 색인을
**한 DB, 한 트랜잭션**에 담는다. 운영 대상이 하나 줄고, 나중에 접근 권한 필터링을
붙일 때도 일반 SQL `WHERE` 절로 해결된다.

**포기한 것.** 대규모(수천만 청크) 구간의 검색 성능. pgvector의 HNSW 색인은
PoC 규모(수만~수십만 청크)에서는 충분하며, 한계에 부딪히면 그때 옮기면 된다.
지금 미리 최적화할 근거가 없다.

---

## D3. 임베딩은 로컬 고정, 생성은 교체 가능

**결정.** 임베딩은 `bge-m3`로 고정. 생성 모델만 교체 가능하게 설계.

**근거.** 두 가지 이유가 겹친다.

*보안.* 색인 단계에서는 사내 문서 **전체**가 임베딩 모델을 통과하지만,
생성 단계에서는 질문에 걸린 청크 몇 개만 지나간다. 임베딩만 로컬로 묶어도
외부 노출면이 크게 줄어든다.

*실용.* 임베딩 모델을 바꾸면 벡터 공간이 달라져 **전체 재색인이 필요하다.**
생성 모델은 언제든 바꿀 수 있다. 성질이 다른 두 결정을 묶어두면
생성 모델 하나 바꾸려다 며칠치 재색인을 하게 된다.

참고로 Anthropic API에는 자체 임베딩 엔드포인트가 없다. Claude를 쓰더라도
임베딩은 별도로 조달해야 하므로, 이 분리는 선택이 아니라 사실상 전제다.

**포기한 것.** 임베딩 품질의 상한. 상용 임베딩 API가 더 나을 수 있지만,
`bge-m3`는 다국어·한국어 지원이 준수하고 8192 토큰 컨텍스트를 지원한다.

---

## D4. 모델 런타임은 Ollama 하나로 통합

**결정.** 임베딩과 생성을 모두 Ollama로 서빙.

**근거.** `bge-m3`와 채팅 모델을 같은 런타임에서 돌릴 수 있다. 노트북 환경에서
컨테이너 하나를 줄이는 효과가 있고, 모델 교체가 `ollama pull`로 끝난다.

**포기한 것.** 추론 처리량. vLLM이 동시 요청 처리에서 낫지만, PoC는 단일 사용자다.
사내 서버로 옮기며 동시 사용자가 생기면 그때 vLLM을 검토한다.

---

## D5. 검색은 처음부터 하이브리드

**결정.** 벡터 검색 + 전문검색을 RRF로 결합. 단계적 도입 아님.

**근거.** 이 회사의 도메인 특성 때문이다. 하드웨어 인프라 문서에는 모델명,
파트번호, 규격 코드, 펌웨어 버전 같은 **정확한 식별자**가 대량으로 등장한다.
벡터 검색은 `DDR5-4800`과 `DDR5-5600`을 거의 구분하지 못한다.
"A6000 전력 소비량"에 A5000 문단을 반환하는 실패가 실제로 나온다.

일반적인 RAG 가이드는 "벡터로 시작하고 필요하면 하이브리드"를 권하지만,
이 도메인에서는 그 "필요"가 거의 확실하다. 나중에 붙이면 평가셋을 다시 돌려야 한다.

**포기한 것.** 초기 구현 단순함. 검색 경로가 둘이 되고 결합 로직이 필요하다.

**미해결.** PostgreSQL 기본 전문검색에는 한국어 형태소 분석기가 없다.
`simple` 설정 + `pg_trgm`으로 시작한다. 영문·숫자 식별자에는 충분하지만
한국어 조사 처리는 부정확하다. **평가 단계에서 실제로 문제가 되는지 확인한 뒤**
형태소 분석기 도입을 결정한다. 지금 넣지 않는 이유는 구성 요소가 늘기 때문이다.

## D6. IaC는 지금 작성하지 않음

**결정.** `infra/` 디렉터리를 만들지 않는다. `compose.yaml` 하나로 시작.

**근거.** 배포 대상이 아직 정해지지 않았다. 사내 VM인지, 쿠버네티스인지,
클라우드인지에 따라 Ansible·Helm·Terraform으로 갈린다. 대상 없이 미리 쓴 IaC는
대체로 버려진다.

하드웨어 인프라 회사인 만큼 최종적으로 IaC 비중이 커질 것으로 예상하지만,
**지금 준비할 것은 IaC 파일이 아니라 IaC를 쉽게 얹을 수 있는 상태**다.
구체적으로 두 가지를 지킨다.

- 모든 설정을 환경변수로 외부화한다 (코드에 하드코딩 없음)
- 상태를 컨테이너 밖 볼륨에 둔다 (재생성 가능한 컨테이너)

이 두 가지가 지켜지면 나중에 어떤 도구를 쓰든 얹기 쉽다.

**포기한 것.** 없음. 배포 대상이 정해지면 그때 착수한다.

---

## D7. "모른다"고 답하는 것을 평가 항목에 포함

**결정.** 근거가 없으면 답변을 생성하지 않도록 제약하고, 이를 측정한다.

**근거.** 사내 지식 시스템에서 가장 큰 위험은 답변이 없는 것이 아니라
**그럴듯한 거짓 답변**이다. 출장비 상한이나 장비 규격을 지어내면 실제 업무 손실로
이어지고, 한 번 겪은 사용자는 시스템을 다시 쓰지 않는다.

그래서 평가셋에 **문서에 답이 없는 질문**을 의도적으로 섞고,
"찾지 못했다"고 답한 비율을 별도 지표로 기록한다.

**포기한 것.** 답변률. 보수적으로 동작하면 "모르겠다"가 늘어난다.
PoC 단계에서는 이쪽이 옳은 트레이드오프라고 판단했다.

---

## D8. 인증과 문서별 접근 권한을 PoC 범위에 포함

**결정.** 환경변수 API 키로 주체(역할 + 소속 그룹)를 만들고, 문서의
`acl_groups` 와 교집합이 있을 때만 검색·열람을 허용한다. 역할은
`reader < editor < admin` 세 단계.

**근거.** 처음에는 범위 밖으로 뒀지만, 사내 문서를 실제로 올려 보는 순간
막힌다. 규정집·단가표·인사 문서가 섞이면 "전사 공개 아님"이 즉시 문제가 되고,
권한 없이 한 번 색인한 코퍼스는 나중에 권한을 얹을 때 전부 다시 판정해야 한다.
검색 단계에서 `WHERE` 절 하나로 끝나는 구조(pgvector 를 고른 이유, D2)를
지금 증명해 두는 편이 싸다.

키를 DB 가 아니라 환경변수에 둔 것은 PoC 에서 사용자 관리 화면을 만들 이유가
없기 때문이다. 사내 SSO 를 붙일 때 `app/security.py` 만 교체하면 된다.

**포기한 것.** 사용자 자가 등록, 키 회전, 그룹 계층. 키가 늘면 환경변수가
지저분해진다. 그 시점이 SSO 연동 시점이다.

## D9. 한국어 질의는 형태소 분석기 대신 용어집으로 확장

**결정.** 질문에서 조사를 규칙으로 떼고, 사내 용어집(`glossary.yaml`)으로
한국어 어휘를 영문 문서 표현으로 바꿔 희소 검색에 넣는다. 전문검색 어휘는
AND 가 아니라 **OR** 로 묶는다.

**근거.** D5 에서 "한국어 형태소 분석기 부재가 실제로 문제가 되는지 평가에서
확인한다"고 미뤄 뒀다. 확인해 보니 문제는 형태소 분석기가 아니라 **언어
불일치**였다. 문서는 전부 영문이고 질문은 한국어다. "메모리"라는 토큰은 영문
문서에 아예 없으므로, 형태소 분석을 완벽히 해도 희소 검색은 0건이다.

게다가 `websearch_to_tsquery` 는 어절을 AND 로 묶는다. 한국어 질문을 그대로
넣으면 결과가 항상 0건이 되어, 하이브리드 검색이라 부르면서 실제로는 밀집
검색 하나로 돌고 있었다. 하필 죽은 쪽이 모델명·파트번호에 강한 경로다.

용어집 쪽이 나은 이유가 둘 더 있다. 컨테이너를 늘리지 않는다. 그리고 못 찾은
질문의 단어를 실무자가 직접 한 줄 추가할 수 있다 — 코드 배포 없이 품질이
오르는 경로는 이것뿐이다.

**포기한 것.** 순수 한국어 문서 코퍼스에서의 품질. 사내 한국어 문서가 주가
되면 형태소 분석기(또는 bigram 색인)를 다시 검토해야 한다. 지금 판단 근거는
"이 코퍼스는 영문"이다.

## D10. 리랭킹은 규칙 기반을 기본으로, 교차 인코더는 보류

**결정.** `RERANK_PROVIDER=rules` 를 기본값으로 둔다. 특징 점수(식별자 일치,
제품 태그 일치, 항목명 자리 일치, 청크 종류, 경로 합의)로 후보 30개를
재정렬한다. LLM 리랭커(`llm`)는 선택으로 제공한다.

**근거.** `bge-reranker-v2-m3` 는 품질이 좋지만 Ollama 가 리랭킹
엔드포인트를 주지 않아 런타임을 하나 더 띄워야 한다. 구성요소를 늘리지 않는다는
원칙(architecture.md 1.1)이 우선이다.

규칙 리랭커를 쓸 만하게 만든 신호는 **"묻는 항목이 값이 아니라 항목명 자리에
있는가"** 였다. 실측 예: "SR630 V4 최대 메모리 용량" 질문에

```
1위(전)  Comparing the SR630 V4 to the SR630 V3 | Feature: Memory | ...
2위(전)  Standard specifications | Memory maximum: Up to 8TB ...   ← 정답
```

앞의 행은 `Memory` 가 **값**이고 뒤는 **항목명**이다. 항목명 일치에 가중을
주자 정답이 1위로 올라왔다. 이 코퍼스는 키-값 사양표가 대부분이므로 일반적인
신호이며, 무엇보다 **왜 1위인지 설명할 수 있다.** 사내 도입 검토에서 반드시
받는 질문이다.

**포기한 것.** 교차 인코더 수준의 상한. 평가에서 규칙 리랭커의 Recall 이
천장에 닿으면 그때 별도 런타임을 검토한다.

## D11. 스키마는 단일 `schema.sql` 대신 번호 붙은 마이그레이션

**결정.** `app/db/migrations/NNN_*.sql` + `python -m app.db.migrate`.
모든 문장은 재실행 가능하게 쓰고, 파일 끝에서 자기 버전을 `schema_migrations`
에 남긴다.

**근거.** 단일 `schema.sql` 은 컨테이너 initdb 에서만 실행되므로, 스키마를
바꾸려면 볼륨을 지워야 한다. 그것은 첫 데모까지만 통한다. 787페이지를 다시
색인하는 비용이 붙는 순간 아무도 스키마를 고치지 않게 되고, 그때부터 설계가
굳는다.

파일 끝에 버전 기록을 넣은 것은 initdb(디렉터리를 번호순 실행)와 파이썬
러너가 **같은 파일로 같은 결과**를 내게 하기 위해서다. 스키마 정의가 두 곳에
갈라지는 것을 원천적으로 막는다.

**포기한 것.** 롤백(down) 스크립트. PoC 에서 되돌릴 일보다 앞으로 나갈 일이
많고, 되돌릴 수 없는 마이그레이션은 아직 없다.

## D12. 색인은 작업 큐로 옮기고, API 는 동기 유지

**결정.** 업로드·동기화는 `ingest_jobs` 에 작업을 만들고 스레드 풀에서
처리한다. 진행 상황은 `GET /jobs/{id}`. 반면 FastAPI 핸들러는 `async` 로
바꾸지 않고 동기 함수로 유지한다.

**근거.** 두 결정이 반대 방향처럼 보이지만 이유는 같다 — 비용 대비 효과다.

색인은 노트북에서 수십 분이 걸린다. HTTP 요청 안에서 처리하면 프록시
타임아웃에 걸리고 진행 상황을 볼 수 없다. 큐가 필요하다. 단, Redis·Celery 를
넣지 않는다. 상태는 DB 에 있으므로 프로세스가 죽어도 무엇이 돌다 말았는지
남고, 나중에 워커만 분리하면 된다.

반대로 요청 경로를 전부 `async` 로 바꾸는 것은 검색·생성·DB 계층을 모두 고쳐야
하는 큰 변경인데, 얻는 것은 동시 사용자 수십 명 구간의 처리량이다. FastAPI 는
동기 핸들러를 스레드 풀에서 돌리므로, 연결 풀(D2 의 pgvector 한 DB)만 있으면
PoC 규모에서는 충분하다. 동시 사용자가 실제로 병목이 되면 그때 vLLM 검토(D4)와
함께 다룬다.

**포기한 것.** 고부하 구간의 처리량. 그리고 작업 큐가 단일 프로세스 안에
있으므로 인스턴스를 늘리면 워커 분리가 필요하다.

---

## D13. 답변의 수치를 발췌와 문자열로 대조한다

**결정.** 생성된 답변에서 수치·식별자를 뽑아 인용한 발췌 안에 실제로 있는지
확인한다. 없으면 `grounded=false` 로 표시하고, `GROUNDING_MODE=strict` 면
답변을 보류한다.

**근거.** 인용 번호 검증(기존)은 "출처를 댔는가"만 본다. 실무에서 가장 잘
일어나는 실패는 **출처는 맞는데 숫자가 틀린 답변**이고, 출처가 붙어 있어서
오히려 더 위험하다. 8TB 를 4TB 로 적은 스펙 답변은 그대로 견적에 들어간다.

의미 검증이 아니라 표기 검증으로 좁힌 것이 요점이다. 문장 표현은 바꿔 쓰는
것이 정상이지만 스펙 값은 바꿔 쓸 이유가 없다. 그래서 오탐이 적고, 규칙을
설명할 수 있다.

기본값을 `strict` 가 아니라 `warn` 으로 둔 이유: 근거 없는 값을 **보여 주면서
표시**하는 편이 조용히 "찾지 못했습니다"로 바꾸는 것보다 PoC 기간에 배울 것이
많다. 어떤 값이 왜 어긋났는지 로그에 남는다.

**포기한 것.** 문장 단위 사실 검증. 그것은 별도 판정 모델이 필요하고, 그
모델의 정확도를 다시 검증해야 한다.

## D14. 질의 로그와 사용자 평가를 DB 에 남긴다

**결정.** 모든 질의를 `query_log` 에 기록한다(질문, 주체, 필터, 근거 청크,
단계별 지연, 근거 검증 결과). `POST /feedback` 으로 맞음/틀림을 받고,
`GET /admin/queries?only_failed=true` 로 실패한 질문만 본다.

**근거.** architecture.md 8.4 에서 "실패한 질문을 모으는 것이 품질 개선의 가장
빠른 길"이라고 적어 두고 구현은 뒤로 미뤄 뒀는데, 순서가 거꾸로다. PoC 기간
자체가 실패 질문을 모으는 유일한 기회다. 기간이 끝난 뒤에는 "느낌이 별로였다"
말고 남는 것이 없다.

이 로그가 정답표(D7 의 평가셋)의 원천이 된다. 실무자가 실제로 던진 질문 중
실패한 것부터 정답표에 넣으면, 자동 생성 초안의 편향 문제(tools/draft_questions.py
주석)도 자연히 해결된다.

**포기한 것.** 질문 본문이 DB 에 남는다. 사내 질문에 민감 정보가 들어갈 수
있으므로 `QUERY_LOG_ENABLED=false` 로 끌 수 있게 했고, 보존 기간 정책은 사내
규정에 맞춰 정해야 한다.

## D15. 한국어 문서와 영문 문서를 한 색인에 섞는다

**결정.** 질의 확장에서 영문 용어와 **한국어 어간을 함께** 검색어로 쓴다.
다만 `pg_trgm` 경로에는 한 종류만 넣고, 리랭커는 후보 어디에도 없는 어휘를
커버리지 분모에서 제외한다.

**배경.** D9 은 "문서가 영문"을 전제로 용어집을 넣었다. 그 전제가 첫 사내 문서
(회사소개서, 한국어)를 올리는 순간 깨졌다. 한국어 질문을 영문으로만 바꾸면
한국어 문서에서는 희소 검색이 0건이 된다.

코퍼스를 언어별로 나누는 방법도 있지만 택하지 않았다. 사내 문서는 한국어와
영문이 문서 단위가 아니라 **문단 단위로** 섞인다(영문 스펙을 인용한 한국어
제안서). 언어 판정을 색인 단계에 넣으면 그 판정이 틀릴 때 검색이 조용히 빈손이
된다. 양쪽 어휘를 다 넣는 쪽이 실패 모드가 단순하다.

**대가와 그 처리.** 어휘를 늘리면 두 곳이 망가졌고, 둘 다 측정에서 드러났다.

1. **`pg_trgm` 경로가 0건이 됐다.** 이 경로는 문자열 하나를 본문 전체와
   비교하므로 스크립트가 섞이면 `word_similarity` 가 임계값을 넘지 못한다.
   → 영문 어휘가 있으면 그것만 쓰고, 없으면 전부 쓴다.
2. **리랭커의 커버리지 비율이 희석됐다.** 후보 어디에도 없는 어휘가 분모에
   끼면 모든 후보 점수가 똑같이 줄고, 그만큼 검색 순위 항의 비중이 커져
   순서가 뒤집힌다. 정답(`Weight: Maximum weight: 42 kg`)이 2위로 밀렸다.
   → 후보 전체에 한 번도 안 나오는 어휘는 변별 정보가 0 이므로 분모에서 뺀다.

고치기 전 영문 평가셋에서 Recall@1 이 0.784 → 0.757 로 떨어졌고, 두 수정
후 0.784 로 복귀했다. **측정 없이 넣었으면 한국어를 얻고 영문을 잃은 것을
몰랐을 것이다.**

**포기한 것.** 한국어 형태소 분석 품질. 조사 제거는 규칙 기반이고 용언 어미는
불용어 목록으로 막는다. 한국어 문서가 코퍼스의 주가 되면 형태소 분석기 또는
bigram 색인을 다시 검토해야 한다.

## D16. 표의 세로 병합 셀을 채운다

**결정.** 추출된 표에서 첫 열이 빈 데이터 행은 직전 행의 라벨로 채운다.

**근거.** 세로 병합 셀은 추출 결과에서 첫 행에만 값이 남는다. 행 단위로 청크를
만드는 이 설계에서는 그 행이 무엇에 관한 값인지 잃는다.

```
구분: 매출액 | 시스템구축 | 2025년: 6,543,210   ← 라벨이 있는 행
            | 기술용역외 | 2025년:  3,333,333   ← 라벨 유실
            | 합계      | 2025년: 9,876,543   ← 라벨 유실(정답)
```

"2025년 매출액"을 물었더니 라벨이 남은 첫 행만 검색되어 **시스템구축 소계를
매출 합계로 답했다.** 인용한 출처는 정확했고 근거 검증도 통과했다 — 그 숫자가
실제로 그 발췌에 있었기 때문이다. 표기 검증(D13)이 잡을 수 없는 종류의 오답이고,
이런 답이 그대로 견적이나 보고서에 들어간다.

행 단위 청킹을 포기하는 대안도 있었다(표 전체를 한 청크로). 그러면 자기완결성을
잃고 큰 표가 컨텍스트를 다 먹는다. 라벨을 채우는 쪽이 싸고 효과가 확실하다.

**측정.** 영문 제품 가이드 6건에서 내용이 바뀐 청크는 문서당 0~5개였고
(`Field upgrades`, `Network adapters` 표의 세로 병합), 평가 지표는 변하지 않았다.
한국어 회사소개서에서는 의도한 2행이 정확히 바뀌었다.

**포기한 것.** 가로 병합 셀. 그리고 라벨이 실제로 바뀌는 행을 빈 셀로 표현한
표라면 잘못 채운다. 이 문서군에서는 그런 표를 보지 못했다.

## D17. 표의 단위 표기를 모든 행에 붙인다

**결정.** 표가 있는 페이지의 본문에서 `(단위:천원)` 같은 표기를 찾아 그 페이지
표의 **모든 행 청크**에 주석으로 붙인다.

**근거.** "2025년 총매출액"에 `9,876,543원` 이라고 답했다. 문서의 단위는
**천원**이므로 실제는 약 168.5억원이다 — **1000배 오차**다.

값을 그대로 옮기라는 규칙(answer.py 4)을 지켜도, 근거 검증(D13)을 통과해도
이렇게 된다. 숫자는 발췌에 그대로 있었고 출처도 정확했다. 문제는 **값을 읽는
단위가 다른 청크에 있었다**는 것이다. 단위 표기는 표 안이 아니라 슬라이드
본문(캡션)에 있어서, 행 단위 청크가 구조적으로 놓친다.

D16(세로 병합)과 같은 계열의 실패다. 행 단위 청킹은 자기완결성을 얻는 대신
표 바깥의 맥락을 잃는다. 그 맥락 중 **값의 해석을 바꾸는 것**은 반드시 행에
붙여야 한다.

**측정.** 영문 제품 가이드 6건은 변경된 청크가 **0개**였다(단위를 본문 캡션에
쓰지 않는 문서군). 한국어 회사소개서는 재무표 11행이 바뀌었고, 같은 질문에
이제 `9,876,543 천원` 이라고 답한다.

**포기한 것.** 한 페이지에 단위가 다른 표가 둘 있으면 잘못 붙인다. 값이 아니라
주석으로 붙이고 출처 표시로 원문 확인 경로를 남기는 선택이다. 표 내부 캡션과
표 바깥 캡션을 구분하지도 않는다(bbox 비교가 필요하고, 이득이 불확실하다).
