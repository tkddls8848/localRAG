# 아키텍처 설계

## 1. 설계 원칙

이 PoC는 소프트웨어 제품이 아니라 **검증 도구**다. 다만 "검증 도구"가 노트북
데모를 뜻하지는 않는다. 사내 문서를 실제로 올려 보고, 실무자가 실제로 질문하고,
그 결과를 숫자로 보고해야 결론이 난다. 그래서 네 가지를 우선한다.

1. **구성 요소 최소화** — 컨테이너가 늘어날수록 나중에 사내 서버로 옮길 때
   비용이 커진다. 상주 컨테이너는 3개(app, postgres, ollama)로 끝난다.
   마이그레이션과 모델 내려받기는 한 번 돌고 끝나는 작업으로 분리했다.
2. **교체 지점의 국소화** — 모델 제공자가 아직 미정이므로, 바뀔 수 있는 부분을
   `app/providers/` 한 곳에 가둔다. 나머지 코드는 제공자를 알지 못한다.
   인증도 같은 이유로 `app/security.py` 한 곳에 가둔다(사내 SSO 교체 지점).
3. **출처 없는 답변은 실패로 간주** — 사내 지식 시스템은 답변이 그럴듯한 것보다
   "어느 문서 몇 페이지에서 나왔는지"를 대는 것이 신뢰의 조건이다. 한 걸음 더
   나아가, 답변의 **수치가 그 발췌 안에 실제로 있는지**까지 대조한다.
4. **실패를 관측 가능하게** — 색인된 줄 알았는데 빠져 있는 문서, 답을 못 찾은
   질문, 근거 없는 수치. 이 세 가지가 목록으로 남아야 다음에 무엇을 고칠지
   추측하지 않는다.

## 3. 구성 요소

### 3.1 수집 · 색인 (`app/ingest/`)

```
파일 → 파싱 → 청킹 → 임베딩 → 적재
```

**파싱.** PDF는 `PyMuPDF`로 텍스트와 페이지 번호를 함께 추출한다.
페이지 번호는 출처 표시의 핵심이므로 파싱 단계부터 끝까지 유지한다.
Office 문서는 `python-docx` / `openpyxl` / `python-pptx`로 처리한다.
DOCX/XLSX는 렌더링 페이지가 없으므로 `page_from/page_to=0`을 사용하고,
섹션 경로의 문단·표·시트·행으로 출처를 표시한다. PPTX는 슬라이드 번호를 쓴다.

표가 많은 사내 문서(장비 스펙표, 단가표)는 텍스트로 평탄화하면 의미가 무너진다.
표는 열 이름(Office는 셀 좌표 또는 열 번호)과 값을 짝지어 행 단위로 저장한다.

**세로 병합 셀을 채운다.** 추출된 표에서 세로 병합은 첫 행에만 값이 있고 나머지
행은 비어 있다. 행 단위로 청크를 만드는 구조에서는 그 행이 무엇에 관한 값인지
잃는다. 실제로 겪은 오답:

```
구분: 매출액 | 시스템구축 | 2025년: 6,543,210   ← 라벨이 있는 행
            | 기술용역외 | 2025년:  3,333,333   ← 라벨 유실
            | 합계      | 2025년: 9,876,543   ← 라벨 유실(정답)
```

"2025년 매출액"을 물으면 라벨이 남은 첫 행만 걸려 **소계를 합계로 답한다.**
출처는 맞는데 값이 틀린, 가장 위험한 실패다. 그래서 첫 열이 빈 데이터 행은
직전의 라벨로 채운다.

**반복 머리말·꼬리말 제거.** 이 문서군은 모든 페이지에 같은 꼬리말이 있다.
실측: 156페이지 문서에서 `Lenovo ThinkSystem SR# V# Server #` 가 156회,
그다음으로 잦은 실제 표 헤더가 42회였다. 그대로 색인하면 문서당 수백 개의 동일
청크가 생겨 검색 결과 상단을 의미 없는 행이 차지한다. **페이지 절반 이상에
등장하는 짧은 텍스트**를 상용구로 판정해 제거한다. 실측 분포에서 본문과 상용구
사이에 넓은 간격이 있어 오제거 위험이 없다.

**스캔 PDF 판정.** 페이지당 추출 문자가 임계 미만이면 스캔 PDF 로 의심하고
`documents.meta.needs_review` 에 표시한다. OCR 은 이번 범위가 아니지만,
**조용히 빈 색인을 만들지는 않는다.** 색인된 줄 알았는데 빠져 있는 문서가
PoC 에서 가장 위험하다.

**청킹.** 문서 구조(TOC → 절 → 문단)를 따라 자른다. 표 행은 그 자체로 완결된
사실이므로 쪼개지도 합치지도 않는다. 각 청크 앞에 **제품명과 섹션 경로**를
붙여 단독으로 읽히게 만든다. 이것이 모델 혼동을 막는 1차 방어선이다.

```
ThinkSystem SR680a V4 > Standard specifications
Memory maximum: Up to 4TB by using 32x 128GB RDIMMs
```

청크마다 `content_hash`(제품 + 본문)와 근사 토큰 수를 함께 저장한다. 앞의 것은
검색 결과에서 같은 사실을 여러 건 돌려주지 않기 위한 키이고, 뒤의 것은 컨텍스트
예산 계산에 쓴다.

**임베딩.** `bge-m3`, 1024차원. 로컬 고정.

> **임베딩 모델을 바꾸면 전체 재색인이 필요하다.** 생성 모델은 언제든 교체할 수
> 있지만 임베딩 모델은 그렇지 않다. 무엇이 재색인을 요구하는지는
> [operations.md 10](operations.md)의 표에 정리했다.

**작업 큐와 동기화.** 787페이지 6건의 임베딩은 노트북에서 수십 분이 걸린다.
HTTP 요청 안에서 처리하면 프록시 타임아웃에 걸리므로, 업로드와 디렉터리 동기화는
`ingest_jobs` 에 작업을 만들고 스레드 풀에서 처리한다. 진행 상황은
`GET /jobs/{id}`. 동기화는 경로·크기·수정시각 → 해시 → 색인 순으로 판정해
**변경된 파일만** 다시 색인하고, 내용이 바뀐 파일은 이전 판을 지운다.

**실패 처리.** 재색인은 새 임베딩이 전부 준비된 뒤 한 트랜잭션에서 청크를
교체한다. 중간에 실패하면 이전 청크가 그대로 검색되고 `documents.error` 에
원인이 남는다. 모델이 죽은 동안 검색이 빈손이 되는 것보다 낫다.

### 3.2 검색 (`app/retrieval/`)

**질의 분석이 먼저다.** 검색에 넣기 전에 질문에서 네 가지를 뽑는다.

| 추출 | 쓰임 |
|---|---|
| 제품 모델 | 모델을 특정한 질문에 다른 모델 청크가 섞이는 것을 차단(2차 방어선) |
| 식별자 | 파트번호·피처코드·규격·수치. 정확 일치 경로의 입력 |
| 검색어 | 조사 제거 + **용어집으로 한국어 → 영문 문서 표현 확장** |
| 의도 | spec / procedure / comparison / general. 리랭킹 기준이 달라진다 |

**한국어 어간은 영문 확장과 함께 남긴다.** 코퍼스에 한국어 문서(사내 소개서,
규정집)가 섞이면 영문 용어만으로는 희소 검색이 한 건도 맞히지 않는다. 반대로
영문 문서에는 한국어 어휘가 없어 매칭에 영향을 주지 않으므로, 양쪽을 다 넣는
것이 안전하다. 다만 두 가지를 함께 지켜야 한다.

- `pg_trgm` 경로에는 한 종류만 넣는다. 이 경로는 문자열 하나를 본문 전체와
  비교하므로 스크립트가 섞이면 유사도가 임계값 아래로 떨어져 **후보가 0건**이
  된다(실측에서 겪음)
- 리랭커는 **후보 어디에도 없는 어휘를 커버리지 분모에서 뺀다.** 그러지 않으면
  모든 후보가 똑같이 희석되고 그만큼 검색 순위의 영향이 커져 순서가 뒤집힌다

용어집 확장이 이 문서군에서 결정적이다. 문서는 전부 영문이고 질문은 한국어다.
"메모리"라는 토큰은 영문 문서에 없으므로, 확장 없이는 희소 검색이 0건이다.
게다가 `websearch_to_tsquery` 는 어절을 AND 로 묶으므로 한국어 질문을 그대로
넣으면 결과가 항상 비어 있다. 즉 하이브리드 검색이라 부르면서 실제로는 밀집
검색 하나로 도는 상태가 되며, 하필 죽은 쪽이 식별자에 강한 경로다(decisions.md D9).

**네 경로를 병행하고 가중 RRF 로 합친다.**

| 경로 | 방식 | 강점 |
|---|---|---|
| dense | pgvector 코사인 (HNSW) | 표현이 달라도 의미로 찾음 |
| sparse | `content_tsv` OR + `ts_rank_cd` | 여러 어휘가 겹치는 문단 |
| exact | 식별자 전량 AND | 파트번호·피처코드 단건 조회 |
| trigram | `pg_trgm` `word_similarity` | 표기 흔들림·부분 일치 보완 |

`exact` 를 따로 둔 이유: OR 결합만 쓰면 "CF3G" 를 물었을 때 CF 가 들어간 수백
행이 같은 취급을 받는다. 식별자가 있는 질문은 그 식별자를 모두 포함한 청크가
정답일 확률이 압도적이므로 가장 높은 가중을 준다.

결합 결과에 세 가지 후처리를 한다.

- **중복 제거** (`content_hash`) — 같은 사실이 컨텍스트 자리만 차지하지 않게
- **결과 다양화** — 근접 중복(본문 토큰 유사도)과 **섹션별 상한**으로 한 표가
  상위를 독점하는 것을 막는다. 관련도 순서는 흔들지 않고 초과분만 뒤로 미루며,
  자리가 남으면 원래 순서대로 채운다. 리랭킹 **뒤에** 적용한다 — 후보 단계에서
  줄이면 재정렬이 볼 수 있는 범위가 좁아진다
- **인접 행 부착** — 표 행 청크에 앞뒤 행을 붙인다. 인용은 원래 청크로
  유지하고 본문만 넓힌다. 출처가 흐려지면 안 된다

> 고전적 MMR(관련도와 다양성의 가중합)을 먼저 넣어 봤고, **품질을 크게
> 떨어뜨렸다**(Recall@10 0.76 → 0.54). 모든 청크가 같은 머리(`제품 > 섹션`)를
> 달고 있어 서로 비슷하다고 판정되고, RRF 점수 차이가 작아 다양성 항이 관련도를
> 압도했다. 그래서 "가장 안 비슷한 것" = 질문과 무관한 청크가 1위로 올라왔다.
> 측정 없이 얹은 기법은 품질을 떨어뜨린다(verification.md 6).

**비교 질문은 제품별로 나눠 검색한 뒤 섞는다.** 한 번에 뽑으면 분량이 많은
모델이 상위를 다 먹어 LLM 이 비교할 재료가 없다.

**리랭킹.** 후보 30개를 질문에 맞춰 재정렬한다. 기본은 규칙 기반이다 —
지연이 0 이고 **왜 1위인지 설명할 수 있다.** 사내 도입 검토에서 반드시 받는
질문이기 때문이다. 가장 효과가 컸던 신호는 "묻는 항목이 값이 아니라 **항목명**
자리에 있는가"였다(decisions.md D10). LLM 리랭커는 선택으로 제공하며, 출력이
깨지면 검색 순위를 그대로 유지한다. 리랭커가 검색을 망치는 것이 가장 나쁘다.

### 3.3 생성 (`app/providers/`, `app/retrieval/answer.py`)

검색된 청크를 컨텍스트로 넣고 답변을 생성한다. 신뢰성 방어선을 세 겹으로 둔다.

1. **프롬프트** — 발췌 밖의 사실을 쓰지 말고, 없으면 "찾지 못했습니다"라고 답한다.
   발췌끼리 값이 다르면 임의로 고르지 말고 둘 다 출처와 함께 제시한다.
2. **인용 검증** — 인용 번호가 없거나 범위를 벗어나면 근거 없는 답으로 처리한다.
3. **근거 검증** — 답변의 수치·식별자가 인용한 발췌 안에 실제로 있는지 대조한다.

3번이 실무에서 가장 값지다. 가장 잘 일어나는 실패는 **출처는 맞는데 숫자가
틀린 답변**이고, 출처가 붙어 있어서 오히려 더 위험하다. 8TB 를 4TB 로 적은
스펙 답변은 그대로 견적에 들어간다. 의미 검증이 아니라 표기 검증으로 좁혀
오탐을 줄였다 — 문장 표현은 바꿔 쓰는 것이 정상이지만 스펙 값은 그렇지 않다.

**컨텍스트 예산.** 발췌 합계가 컨텍스트 창을 넘기면 Ollama 가 앞쪽부터
잘라낸다. 앞쪽에는 시스템 규칙이 있으므로, 넘치는 순간 "모르면 모른다고 답한다"는
제약이 가장 먼저 사라진다. 가장 조용하고 위험한 고장이라 여유를 두고 자른다.

**스트리밍.** `POST /ask/stream` 은 출처를 먼저 보내고 본문을 토큰 단위로
흘린다. 검증과 스트리밍은 원리적으로 상충한다 — 마지막 토큰을 받기 전에는
인용과 근거를 확인할 수 없다. 그래서 본문은 흘리되 마지막 `done` 이벤트에 검증
결과를 담고 화면이 그때 경고를 띄운다. 검증을 포기하지 않으면서 체감 지연을
줄이는 타협이다.

### 3.4 접근 권한 (`app/security.py`)

API 키 → 주체(역할 + 소속 그룹). 문서의 `acl_groups` 와 주체 그룹의 교집합이
있을 때만 검색·열람을 허용한다. 빈 배열은 전사 공개다.

판정은 **검색 SQL 안에서** 일어난다.

```sql
AND (:groups::text[] IS NULL
     OR cardinality(d.acl_groups) = 0
     OR d.acl_groups && :groups::text[])
```

애플리케이션이 결과를 받아 걸러내는 방식이 아니므로 경로를 우회할 수 없다.
메타데이터와 벡터를 한 DB 에 둔 선택(decisions.md D2)의 직접적인 이득이다.

### 3.5 관측 (`app/observability.py`)

- 모든 로그 줄에 `request_id`. `LOG_FORMAT=json` 이면 수집기에 그대로 넣는다
- 단계별 지연을 분리 기록(embed / search / rerank / generate). 느린 것을
  품질 문제로 오진하지 않기 위해서다
- `GET /metrics` Prometheus 텍스트 형식. 의존성을 늘리지 않기 위해 직접 만든다
- `query_log` 에 모든 질의를 남기고 `POST /feedback` 으로 맞음/틀림을 받는다.
  PoC 기간이 실패 질문을 모으는 유일한 기회다(decisions.md D14)

### 3.6 API (`app/api/`)

| 엔드포인트 | 최소 역할 | 용도 |
|---|---|---|
| `GET /` | – | 운영 콘솔(질문 / 진단 / 문서 / 운영) |
| `POST /ask` | reader | 질문 → 답변 + 출처 + 근거 검증 결과 |
| `POST /ask/stream` | reader | 같은 동작의 SSE 스트리밍 |
| `POST /search` | reader | **답변 없이 검색 후보만.** 왜 못 찾았나를 조사 |
| `POST /feedback` | reader | 답변 평가(맞음/틀림) |
| `POST /ingest` | editor | 파일 업로드. 기본은 작업 등록, `?wait=true` 로 동기 |
| `GET /jobs`, `GET /jobs/{id}` | reader | 색인 작업 진행 상황 |
| `GET /documents` | reader | 색인된 문서와 상태(열람 권한 범위 안에서) |
| `DELETE /documents/{id}` | editor | 잘못 색인된 문서 제거 |
| `POST /admin/sync` | admin | 서버 디렉터리 동기화. `?dry_run=true` 로 계획만 |
| `GET /admin/queries` | admin | 질의 로그. `?only_failed=true` |
| `GET /admin/stats` | admin | 응답률·지연 백분위·프로세스 지표 |
| `GET /health`, `GET /ready` | – | 상태 확인. `/ready` 는 스키마·모델·차단기까지 |
| `GET /metrics` | – | Prometheus. **인증이 없으므로 외부 노출 금지** |

`/ask` 응답에는 답변 본문과 함께 참조한 청크의 **문서명·페이지·원문 일부**를
반드시 포함한다. 사용자가 원문을 직접 확인할 수 있어야 한다.

## 4. 데이터 모델

스키마는 `app/db/migrations/NNN_*.sql` 에 있고 `python -m app.db.migrate` 로
적용한다. 모든 문장은 재실행 가능하며, 파일 끝에서 자기 버전을
`schema_migrations` 에 남긴다. 컨테이너 initdb(디렉터리를 번호순 실행)와 파이썬
러너가 **같은 파일로 같은 결과**를 내게 하기 위한 구조다(decisions.md D11).

```sql
documents
  id, source_path, title, products text[], sha256 UNIQUE,
  page_count, status,            -- pending|indexing|indexed|failed
  error, meta jsonb,             -- warnings, needs_review, 색인 당시 설정
  acl_groups text[],             -- 빈 배열 = 전사 공개
  source_kind, byte_size, source_mtime,   -- 변경분 판정용
  ingested_at, updated_at

chunks
  id, document_id → documents ON DELETE CASCADE,
  ordinal, kind,                 -- table_row | prose
  content, section_path, page_from, page_to,
  products text[],               -- 본문이 한 모델만 가리키면 좁혀 저장
  embedding vector(1024),
  content_hash,                  -- 같은 사실 중복 제거
  token_count,                   -- 컨텍스트 예산
  content_tsv tsvector GENERATED ALWAYS AS (to_tsvector('simple', content)) STORED
  UNIQUE (document_id, ordinal)  -- 인접 행 조회에도 쓰인다

query_log      -- 질문, 주체, 필터, 근거 청크, 단계별 지연, 근거 검증, 사용자 평가
ingest_jobs    -- 작업 종류·상태·진행률. 프로세스가 죽어도 무엇이 돌다 말았는지 남는다
schema_migrations
```

색인:

```sql
chunks USING hnsw (embedding vector_cosine_ops)   -- 밀집
chunks USING gin (content_tsv)                    -- 희소·정확 일치
chunks USING gin (content gin_trgm_ops)           -- 유사도
chunks USING gin (products)                       -- 모델 혼동 차단
documents (status), documents USING gin (acl_groups)
query_log (asked_at DESC) WHERE answered = false  -- 실패 질문 조회
```

`content_tsv` 를 생성 컬럼으로 둔 이유: `ts_rank_cd` 를 정렬에 쓰면 함수 색인만
으로는 매 행마다 `to_tsvector` 를 다시 계산한다. 저장 컬럼이면 색인과 정렬이
같은 값을 쓴다.

설계상 짚어둘 점:

- `sha256`으로 **같은 파일의 중복 색인을 막는다.** 사내 문서는 여러 경로에 같은
  파일이 복사돼 있고, 중복 청크는 검색 결과를 오염시킨다.
- `status`와 `error`를 남겨 **실패한 문서를 추적 가능하게 한다.**
- 문서를 지우면 청크가 함께 지워진다(`ON DELETE CASCADE`).

## 5. 프로바이더 추상화

```
app/providers/
├── base.py       # EmbeddingProvider, LLMProvider 프로토콜
├── ollama.py     # 1차 구현 (재시도 · 차단기 · 스트리밍)
└── fake.py       # 두 번째 구현. 모델 없이 전 경로를 돌린다
```

| 프로토콜 | 메서드 | 비고 |
|---|---|---|
| `EmbeddingProvider` | `embed(texts) -> list[vector]`, `dimension` | 교체 시 재색인 필요 |
| `LLMProvider` | `generate(system, user)`, `generate_stream(...)` | 자유롭게 교체 가능 |

선택은 환경변수로만 한다(`LLM_PROVIDER=ollama`). 코드 수정 없이 바뀌어야
"교체 가능하다"고 말할 수 있다. 인터페이스는 **의도적으로 좁게 유지한다.**
특정 제공자에만 있는 기능을 넣는 순간 추상화가 무너진다.

`fake` 를 테스트 전용이 아니라 정식 두 번째 구현으로 유지한다. 교체 가능성은
두 번째 어댑터를 붙여 보기 전까지 증명되지 않기 때문이다.

**모델 런타임 장애 대비.** PoC 에서 가장 자주 넘어지는 구성요소다. 연결 재사용,
지수 백오프 재시도, 연속 실패 차단기를 넣었다. 죽은 런타임에 요청을 쌓아
대기열만 늘리는 것을 막고, `/ready` 가 차단 상태를 보고한다.

## 6. 로컬 실행 구성

| 서비스 | 이미지 | 상주 | 역할 |
|---|---|---|---|
| `app` | 로컬 빌드 (python:3.12-slim, 비 root) | ○ | FastAPI |
| `db` | `pgvector/pgvector:pg16` | ○ | 저장소 |
| `ollama` | `ollama/ollama` | ○ | 임베딩 + 생성 |
| `migrate` | app 과 동일 | × | 스키마 적용 후 종료 |
| `model-pull` | `ollama/ollama` | × | 모델 내려받기 후 종료 |

`app` 은 `migrate` 가 **성공으로 끝난 뒤에만** 뜬다. 스키마가 덜 적용된 상태로
서버가 올라오는 경우를 없애기 위한 구성이다.

설정은 모두 환경변수로 주입하고 `.env.example`에 전체 목록을 문서화한다.
비밀값은 저장소에 넣지 않는다. 잘못된 설정은 기동 시 검증에서 걸러지고,
위험한 설정(인증 꺼짐, 기본 비밀번호, fake 제공자)은 경고로 남는다.

**노트북 자원 고려.** `bge-m3`는 약 1.2GB, 생성 모델은 7~8B 양자화 기준 약 5GB다.
GPU 없이 CPU만으로도 동작하지만 생성 속도는 느리다. PoC 검증에는 충분하지만
**속도를 품질과 혼동하지 않도록** 평가 시 분리해서 기록한다. 첫 질문이 느린
것은 대개 모델 로딩이므로 `OLLAMA_KEEP_ALIVE` 로 붙잡아 둔다.

향후 사내 서버 배포용 `infra/` 디렉터리는 지금 만들지 않는다(decisions.md D6).
다만 모든 설정을 환경변수로 외부화하고 상태를 볼륨에 두었으므로 나중에
Ansible이든 Helm이든 얹기 쉽다.

## 7. 평가

PoC의 결론은 "돌아간다"가 아니라 **"쓸 만한가"**여야 한다. 그러려면 측정이 필요하다.

**평가셋.** 사내 실무자가 실제로 궁금해할 질문 30~50개를 수집하고, 각 질문마다
정답이 들어 있는 문서와 페이지를 사람이 미리 표시해 둔다. 이 작업이 PoC에서
가장 귀찮지만 가장 중요하다. 이게 없으면 모델을 바꿔도 나아졌는지 알 수 없다.

질문에는 다음을 의도적으로 섞는다.

- 단순 사실 조회 ("최대 메모리 용량이 얼마인가")
- 정확한 식별자 조회 ("CF3G 는 무엇인가") — 하이브리드 검색 검증용
- 모델을 특정한 질문 (SR650 V4 vs SR650a V4 혼동 확인)
- 여러 제품을 비교하는 질문
- **문서에 답이 없는 질문** — 지어내는지 확인용

`query_log` 의 실패 질문을 정답표에 옮기는 것이 가장 좋은 출발점이다.
자동 생성 초안(`tools/draft_questions.py`)은 같은 파이프라인이 만든 문제를 같은
파이프라인이 푸는 구조라 점수가 실제보다 높게 나온다.

**측정 항목.**

| 항목 | 의미 |
|---|---|
| Recall@k | 정답 문단이 상위 k개에 들어오는 비율. **생성 품질의 천장** |
| nDCG@k / MRR | 몇 번째로 맞혔는가. 순서가 나쁘면 LLM 이 놓친다 |
| Precision@k | 가져온 것 중 쓸모 있는 비율. 낮으면 컨텍스트가 소음이다 |
| 답변 정확도 | `expect` 문자열이 답변에 있는가(스펙 값은 자동 채점 가능) |
| 출처 정확도 | 제시한 출처가 실제 정답 위치인가 |
| 근거 일치율 | 답변의 수치가 인용 발췌 안에 있는가 |
| 정직도 | 답이 없는 질문에 "찾지 못했다"고 답한 비율 |
| 응답 시간 | 품질과 분리해 단계별 p50/p95 로 기록 |

**경로별 비교(ablation).** `--modes dense,sparse,exact,hybrid,hybrid+rerank` 로
경로를 하나씩 끄고 켠 표를 만든다. "하이브리드가 낫다"는 주장을 단독 경로 점수와
나란히 놓아야 근거가 된다. 도입 검토에서 결국 요구되는 것이 이 표다.

검색이 실패하면 생성은 무조건 실패한다. 따라서 **Recall을 먼저 본다.**
답변이 나쁠 때 프롬프트부터 손대면 대개 시간을 낭비한다.

`--compare` 로 이전 결과와 나란히 놓고, 2%p 미만의 차이는 개선이라고 부르지
않는다. 질문 30~50개 규모에서 질문 하나가 그만큼을 움직인다.

## 8. 이후 확장

우선순위 순. 앞의 세 항목은 이번에 들어왔다.

- ~~접근 권한~~ → 구현됨 (문서별 열람 그룹, 역할 3단계). 다음은 사내 SSO 연동
- ~~문서 자동 동기화~~ → 디렉터리 동기화 구현됨. 다음은 파일 서버·그룹웨어 연동
- ~~사용 로그 기반 개선~~ → `query_log` + 피드백 구현됨. 다음은 이 로그를
  정답표로 옮기는 주기적 작업
1. **OCR** — 스캔 PDF. 현재는 판정해서 표시만 한다
2. **사내 서버 배포 (IaC)** — 배포 대상 확정 후 착수
3. **여러 인스턴스** — 작업 큐 워커 분리, 요청 제한 공유 저장소
4. **한국어 문서 코퍼스 대응** — 용어집 방식은 "문서가 영문"을 전제한다.
   한국어 문서가 주가 되면 형태소 분석기 또는 bigram 색인을 재검토
