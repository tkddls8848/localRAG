# 아키텍처 설계

## 1. 설계 원칙

이 PoC는 소프트웨어 제품이 아니라 **검증 도구**다. 따라서 세 가지를 우선한다.

1. **구성 요소 최소화** — 컨테이너가 늘어날수록 나중에 사내 서버로 옮길 때 비용이 커진다.
   현재 구성은 컨테이너 3개(app, postgres, ollama)로 끝난다.
2. **교체 지점의 국소화** — 모델 제공자가 아직 미정이므로, 바뀔 수 있는 부분을
   `app/providers/` 한 곳에 가둔다. 나머지 코드는 제공자를 알지 못한다.
3. **출처 없는 답변은 실패로 간주** — 사내 지식 시스템은 답변이 그럴듯한 것보다
   "어느 문서 몇 페이지에서 나왔는지"를 대는 것이 신뢰의 조건이다.

## 3. 구성 요소

### 3.1 수집 · 색인 (`app/ingest/`)

```
파일 → 파싱 → 청킹 → 임베딩 → 적재
```

**파싱.** PDF는 `PyMuPDF`로 텍스트와 페이지 번호를 함께 추출한다.
페이지 번호는 출처 표시의 핵심이므로 파싱 단계부터 끝까지 유지한다.
Office 문서는 `python-docx` / `openpyxl` / `python-pptx`로 처리한다.
DOCX/XLSX는 렌더링 페이지가 없으므로 `page_from/page_to=0`을 사용하고,
섹션 경로의 문단·표·시트·행으로 출처를 표시한다. PPTX는 슬라이드 번호를 사용한다.

표가 많은 사내 문서(장비 스펙표, 단가표)는 텍스트로 평탄화하면 의미가 무너진다.
표는 열 이름(Office는 셀 좌표 또는 열 번호)과 값을 짝지어 행 단위로 저장한다.

스캔된 PDF(이미지만 있는 문서)는 이번 범위에서 제외한다. 다만 텍스트 추출 결과가
비어 있으면 **조용히 넘어가지 않고 실패로 기록**한다. 색인된 줄 알았는데 빠져 있는
문서가 생기는 것이 PoC에서 가장 위험하다.

**청킹.** 문서 구조(제목 → 절 → 문단)를 따라 자르고, 목표 크기는 500~800 토큰,
앞뒤 100 토큰 정도를 겹친다. 각 청크는 소속 문서의 제목과 상위 절 제목을 앞에 붙여서
저장한다. "3.2 동작 온도 범위"라는 청크만 떼어놓으면 어느 장비 이야기인지 알 수 없다.

**임베딩.** `bge-m3`, 1024차원. 로컬 고정.

> **임베딩 모델을 바꾸면 전체 재색인이 필요하다.** 생성 모델은 언제든 교체할 수 있지만
> 임베딩 모델은 그렇지 않다. 그래서 둘의 결정을 분리했고, 임베딩만 먼저 고정한다.

### 3.2 검색 (`app/retrieval/`)

**하이브리드 검색을 기본으로 한다.** 벡터 검색 단독으로 가지 않는 이유가 이 회사의
도메인에 있다.

하드웨어 인프라 문서에는 정확한 식별자가 대량으로 등장한다 — 모델명, 파트번호,
규격 코드, 펌웨어 버전. 벡터 검색은 의미가 비슷한 것을 찾는 데는 강하지만
`DDR5-4800`과 `DDR5-5600`처럼 **한 글자 다른 식별자를 구분하는 데는 약하다.**
"A6000 전력 소비량"을 물었는데 A5000 문단을 가져오는 실패가 실제로 발생한다.

따라서 두 경로를 병행한다.

| 경로 | 방식 | 강점 |
|---|---|---|
| 밀집 검색 | pgvector 코사인 유사도 | 표현이 달라도 의미로 찾음 |
| 희소 검색 | PostgreSQL 전문검색 + `pg_trgm` | 식별자·고유명사 정확 매칭 |

두 결과를 RRF(Reciprocal Rank Fusion)로 합친다. 가중치 튜닝 없이 순위만으로
결합되므로 PoC 단계에 적합하다.

> **알려진 제약:** PostgreSQL 기본 전문검색에는 한국어 형태소 분석기가 없다.
> PoC에서는 `simple` 설정과 `pg_trgm` 기반 유사도로 대응한다. 영문·숫자 식별자에는
> 충분하지만 한국어 조사 처리는 부정확하다. 한국어 키워드 검색 품질이 실제로
> 문제가 되는지 평가 단계에서 확인하고, 필요하면 그때 형태소 분석기 도입을 검토한다.
> 지금 미리 넣지 않는 이유는 구성 요소를 늘리기 때문이다.

**리랭킹은 선택 사항으로 둔다.** `bge-reranker-v2-m3`를 붙이면 정확도가 오르지만
노트북에서는 응답 지연이 체감된다. 기본은 끄고, 검색 품질이 부족할 때 켜서
효과를 측정한다.

### 3.3 생성 (`app/providers/`)

검색된 청크를 컨텍스트로 넣고 답변을 생성한다. 프롬프트의 핵심 제약은 두 가지다.

- 주어진 컨텍스트 안에서만 답한다
- **근거가 없으면 "사내 문서에서 찾지 못했습니다"라고 답한다**

두 번째가 더 중요하다. 사내 규정을 지어내는 시스템은 없느니만 못하다.
평가 항목에도 "모르는 것을 모른다고 답하는 비율"을 넣는다.

### 3.4 API (`app/api/`)

| 엔드포인트 | 용도 |
|---|---|
| `POST /ingest` | 파일 업로드 (최대 50MB). 디렉터리는 CLI에서 색인 |
| `POST /ask` | 질문 → 답변 + 출처 목록 |
| `GET /documents` | 색인된 문서 목록과 상태 |
| `GET /` | 업로드·질의응답 웹 화면 |
| `GET /ready` | DB 스키마와 모델 설치 상태 |

`/ask` 응답에는 답변 본문과 함께 참조한 청크의 **문서명·페이지·원문 일부**를
반드시 포함한다. 사용자가 원문을 직접 확인할 수 있어야 한다.

## 4. 데이터 모델

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE TABLE documents (
    id           bigserial PRIMARY KEY,
    source_path  text        NOT NULL,
    title        text        NOT NULL,
    mime_type    text        NOT NULL,
    sha256       text        NOT NULL UNIQUE,  -- 중복 색인 방지
    page_count   int,
    status       text        NOT NULL,         -- pending|indexed|failed
    error        text,                         -- 실패 원인 보존
    meta         jsonb       NOT NULL DEFAULT '{}',
    ingested_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE chunks (
    id           bigserial PRIMARY KEY,
    document_id  bigint      NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    ordinal      int         NOT NULL,     -- 문서 내 순서
    content      text        NOT NULL,
    section_path text,                     -- "3. 전기적 특성 > 3.2 동작 온도"
    page_from    int,
    page_to      int,
    token_count  int,
    embedding    vector(1024),
    UNIQUE (document_id, ordinal)
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON chunks USING gin (to_tsvector('simple', content));
CREATE INDEX ON chunks USING gin (content gin_trgm_ops);
```

설계상 짚어둘 점:

- `sha256`으로 **같은 파일의 재색인을 막는다.** 사내 문서는 여러 경로에 같은 파일이
  복사돼 있는 경우가 흔하고, 중복 청크는 검색 결과를 오염시킨다.
- `status`와 `error`를 남겨 **실패한 문서를 추적 가능하게 한다.**
  "왜 이 규정은 검색이 안 되지?"에 답할 수 있어야 한다.
- 문서를 지우면 청크가 함께 지워진다(`ON DELETE CASCADE`). 재색인은 새 임베딩이 준비된 후
  트랜잭션에서 청크를 교체한다. 실패하면 기존 색인을 보존하고 `error`에 원인을 기록한다.

## 5. 프로바이더 추상화

```
app/providers/
├── base.py       # EmbeddingProvider, LLMProvider 프로토콜
├── ollama.py     # 1차 구현
└── anthropic.py  # 이후 비교용
```

두 개의 좁은 인터페이스만 정의한다.

| 프로토콜 | 메서드 | 비고 |
|---|---|---|
| `EmbeddingProvider` | `embed(texts) -> list[vector]`, `dimension` | 교체 시 재색인 필요 |
| `LLMProvider` | `generate(system, messages) -> str \| stream` | 자유롭게 교체 가능 |

선택은 환경변수로만 한다 (`LLM_PROVIDER=ollama`). 코드 수정 없이 바뀌어야
"교체 가능하다"고 말할 수 있다.

인터페이스는 **의도적으로 좁게 유지한다.** 특정 제공자에만 있는 기능을 인터페이스에
넣는 순간 추상화가 무너진다. 공통분모만 담고, 필요해지면 그때 넓힌다.

> 실제 교체 가능성은 두 번째 어댑터를 붙여보기 전까지 증명되지 않는다.
> 로컬 모델로 기준선을 잡은 뒤 두 번째 어댑터를 붙여 확인한다.

## 6. 로컬 실행 구성

`compose.yaml` 하나로 전체 스택이 뜬다.

| 서비스 | 이미지 | 역할 |
|---|---|---|
| `app` | 로컬 빌드 (python:3.12-slim) | FastAPI |
| `db` | `pgvector/pgvector:pg16` | 저장소 |
| `ollama` | `ollama/ollama` | 임베딩 + 생성 |

설정은 모두 환경변수로 주입하고 `.env.example`에 전체 목록을 문서화한다.
비밀값은 저장소에 넣지 않는다.

**노트북 자원 고려.** `bge-m3`는 약 2GB, 생성 모델은 7~8B 양자화 기준 약 5GB다.
GPU 없이 CPU만으로도 동작하지만 생성 속도는 느리다. PoC 검증에는 충분하지만
**속도를 품질과 혼동하지 않도록** 평가 시 분리해서 기록한다.

향후 사내 서버 배포용 `infra/` 디렉터리는 지금 만들지 않는다. 배포 대상이
정해지지 않은 상태에서 미리 쓴 IaC는 대체로 버려진다. 다만 모든 설정을
환경변수로 외부화해 두면 나중에 Ansible이든 Helm이든 얹기 쉽다.

## 7. 평가

PoC의 결론은 "돌아간다"가 아니라 **"쓸 만한가"**여야 한다. 그러려면 측정이 필요하다.

**평가셋.** 사내 실무자가 실제로 궁금해할 질문 30~50개를 수집하고, 각 질문마다
정답이 들어 있는 문서와 페이지를 사람이 미리 표시해 둔다. 이 작업이 PoC에서
가장 귀찮지만 가장 중요하다. 이게 없으면 모델을 바꿔도 나아졌는지 알 수 없다.

질문에는 다음을 의도적으로 섞는다.

- 단순 사실 조회 ("출장비 상한이 얼마인가")
- 정확한 식별자 조회 ("A6000 TDP") — 하이브리드 검색 검증용
- 여러 문서를 종합해야 하는 질문
- **문서에 답이 없는 질문** — 지어내는지 확인용

**측정 항목.**

| 항목 | 의미 |
|---|---|
| Recall@10 | 정답 문단이 검색 결과 상위 10개에 들어오는 비율 |
| 답변 정확도 | 사람이 판정 (정확 / 부분 / 오답) |
| 출처 정확도 | 제시한 출처가 실제 근거 문단과 일치하는 비율 |
| 정직도 | 답이 없는 질문에 "찾지 못했다"고 답한 비율 |
| 응답 시간 | 품질과 분리해 기록 |

검색이 실패하면 생성은 무조건 실패한다. 따라서 **Recall을 먼저 본다.**
답변이 나쁠 때 프롬프트부터 손대면 대개 시간을 낭비한다.

## 8. 이후 확장

우선순위 순.

1. **접근 권한** — 사내 문서는 전사 공개가 아니다. 부서·직급별 필터링이
   실서비스의 전제 조건이다. `chunks`에 권한 컬럼을 추가해 검색 단계에서
   거르는 방식이 자연스럽다.
2. **문서 자동 동기화** — 현재는 수동 색인. 파일 서버·그룹웨어 연동 시
   변경분만 재색인하는 구조가 필요하다.
3. **사내 서버 배포 (IaC)** — 배포 대상 확정 후 착수.
4. **사용 로그 기반 개선** — 실패한 질문을 모으는 것이 품질 개선의 가장 빠른 길이다.
